# ADR-0024: Follow-up suggestions are route-templated and carried on their own frame

Status: Accepted
Date: 2026-08-03

## Context

`[chat-model]` Tier 1, output 8: after an answer, offer two or three questions the user might ask
next. Of the three shapes in this batch it is the only one that plausibly needs new wire surface —
outputs 10 and 13 do not, and are recorded in `docs/architecture.md` rather than here.

A suggestion is not decoration in the way a `present` hint is. It is clickable, and clicking it makes
it the next question, which goes into the SQL-generation prompt. So a suggestion is an input path,
and the two questions worth deciding are where its text comes from and how it reaches the client
without becoming the control channel ADR-0023 refused to create.

Both obvious cheap answers fail. Appending "You might also ask: …" to the narration prose and having
the frontend parse it back out is exactly the forgeable marker ADR-0023 rejected for `present`, with
a worse payoff: row text is third-party-controlled post-YNAB-import, and a forged suggestion is
attacker-chosen text the user is invited to click. And a second model call to write the suggestions
moves the forgery from the parser to the generator — the frame is then well-formed and its contents
are still authored from tainted input.

## Decision

**Suggestions are generated by the route from a fixed template set, never by a model, and are
carried on their own NDJSON frame.**

```jsonc
{
  "type": "suggestions",
  "questions": [
    { "text": "How much did I spend on Groceries in June 2026?", "template": "same-filter-prior-period" }
  ]
}
```

- **Templates only.** The template set is a closed list in code. Slot values are restricted to
  things the route already trusts: date ranges it computed itself, and category/account literals
  that are already in ADR-0008/ADR-0018's injected closed vocabulary. Those literals are
  YNAB-sourced, but they already reach the SQL prompt by that route, so this opens no taint path
  that is not already open. Nothing from `rows` and nothing from narration output is ever
  interpolated.
- **Every template must produce a question the pipeline can answer.** No template may generate a
  balance or net-worth question (ADR-0015), a compound-select shape (ADR-0011), or anything else the
  guards refuse. A suggestion the assistant then declines is worse than no suggestion.
- **Preconditions gate each template**, evaluated against the question and the generated SQL:
  `same-filter-prior-period` (a resolved date range exists), `same-filter-longer-window` (the range
  is a month or narrower), `same-period-breakdown` (no category filter and the result is not already
  grouped), `sibling-account` (an account filter is present and more than one account is stored).
  At most three, ordered by that priority.
- **Fails closed and silently.** If the SQL's shape cannot be resolved well enough to fill any
  template, the frame is omitted. Absence of a suggestion is a non-event, which makes this the only
  thing in the pipeline allowed to degrade without saying so.
- **Placement.** Zero or one `suggestions` frame per turn, emitted after `sql`/`result` and before
  the first `token`. The general rule this fixes: **the token stream is always last**, so everything
  after the prose starts is prose, and the client never resumes parsing once it starts rendering
  escaped text.
- **On a refusal, suggestions ride inside the `no-answer` frame** as an optional `questions` array,
  not as a second frame. ADR-0014's invariant is one frame with nothing after it, and that holds
  literally; the array is route-written exactly as `message` is.

## Consequences

**No third inference call.** ADR-0023 declined one for something decidable from data; this declines
one for something decidable from the question and the query. Suggestions cost no tokens and no
latency, which matters under ADR-0006's local-inference budget.

**Suggestions will feel templated, because they are.** Four shapes, deterministic. That is the
trade: a narrow suggestion that always works beats a clever one that sometimes proposes a question
the pipeline declines. If the ceiling turns out to be too low, the fix is Phase B's loop
(ADR-0012/0013) writing them with the session in hand, not a bolted-on second call now.

**A fifth frame type, and a general ordering rule that did not exist before.** `sql`, `result`,
`suggestions`, then `token`s. Previously the ordering was stated per-frame; it is now one invariant,
which is what makes adding a sixth non-prose frame cheap and adding a post-prose frame a decision.

**Suggestions do not persist.** `ChatMessage` stores no such column, so they vanish on reload like
`result` does. Same open question, same answer: whatever resolves it resolves both, and stores the
emitted frame verbatim rather than recomputing it.
